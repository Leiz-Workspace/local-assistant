# ADR-194: Self-hosted GitHub Actions runner on the Home Server

**Purpose:** Let the repository's CI run on the Home Server while staying a normal GitHub Actions workflow with checks on every pull request. Any job can be switched back to GitHub-hosted runners without a code change.

**Date:** 2026-11-12. **Status:** ACCEPTED by the owner's request ("tự host CI và vẫn muốn chạy được trên Github"). The workflow change and the setup kit are implemented and were revised after security reviews before the first install. The owner installed the runner on 2026-11-13. Its first CI run passed on the Home Server (PR #76, run 43302985450); see Validation. **Extended by [ADR-196](196-organization-shared-runner-pool.md) on 2026-11-13:** the repository moved into the `Leiz-Workspace` organization, and the single repository-level runner is replaced by a pool of three organization-level instances of the same hardened unit (`aevra-gh-runner@<n>.service`), shared with `web-cloner-template` and `Mirrix`.

## Context

- **Why CI stopped.** Since early November 2026 every CI run in this private repository has failed within 2–3 seconds with the annotation "The job was not started because recent account payments have failed or your spending limit needs to be increased". No job ran, so PRs were merged on local evidence: the CI-scope pytest run and D87.
- **Billing.** The current GitHub billing documentation lists self-hosted runners as free usage that does not reduce the plan's included compute. Standard GitHub-hosted runners in private repositories draw from that compute.
- **Job requirements.** The test job needs the Home Server layout: `bwrap` with unprivileged user namespaces, ffmpeg, tesseract, poppler, LibreOffice, system CPython 3.12 without the `config-3.12` directory, and Node.js for a few tests.
  - On GitHub-hosted runners the composite action `.github/actions/hosted-python` recreates that layout with `sudo`.
  - The Home Server has the native tools system-wide. Node.js is only in the owner's nvm under `/home`, which D87 reaches because it runs as the owner. The runner user sees neither `/home` nor nvm, so the test jobs install Node.js with `actions/setup-node`.
- **Host constraints.**
  - The host runs Vault, PostgreSQL, Qdrant, Redis, MongoDB, k3s, CORE, models and private data. Several of these listen on loopback or on all addresses.
  - `kernel.apparmor_restrict_unprivileged_userns=1`, so `bwrap` gets user namespaces only through its AppArmor profile.
  - The project sandboxes run `bwrap --unshare-all ... --proc /proc`, and the workspace layer needs `openat2()`.
  - `/tmp` is a 16 GB tmpfs.
  - The owner's home is mode 0750.

## Decision

1. **Runner selection by repository variable.** Every job in `.github/workflows/ci.yml` uses `runs-on: ${{ fromJSON(vars.CI_RUNS_ON || '"ubuntu-24.04"') }}`.
   - Unset: jobs run on GitHub-hosted `ubuntu-24.04`, as before.
   - `["self-hosted","aevra-home"]`: jobs run on the Home Server runner.

   The uv cache path is derived from `$HOME`, so both runner types work.
2. **The composite action handles both runner types** through `runner.environment`.
   - GitHub-hosted: it keeps freeing disk, caching and installing apt packages, and aligning the layout with `sudo`.
   - Self-hosted: it runs a preflight that needs no `sudo` and fails with a clear error. It checks:
     - the tools, `node` included;
     - `/usr/bin/python3.12` and the absence of `config-3.12`;
     - the real sandbox shape, `bwrap --unshare-all --die-with-parent --ro-bind / / --proc /proc --dev /dev --tmpfs /tmp true`, printing bwrap's error;
     - an `openat2()` call with the workspace root's resolve flags;
     - that the GPU device nodes are not accessible;
     - that an `AF_UNIX` connect to tailscaled's LocalAPI socket `/run/tailscale/tailscaled.sock` fails;
     - that TCP connects to the host's own addresses in the denied ranges (from `hostname -I`: LAN, tailnet, Docker and k3s, IPv4 and `fc00::/7`) fail with `EPERM` or time out (added 2026-11-13);
     - a multiprocessing lock, which needs a writable `/dev/shm`.

     The GPU, tailscaled and address checks only detect a sandbox that lost its settings. They control nothing, because code on a branch can change the preflight.
   - `test-python` and `test-python-quarantine` run `actions/setup-node` (`NODE_VERSION`) before the composite action, on both runner types.
   - Every remote action in `ci.yml` and the composite action is pinned to a full commit SHA, with the version in a comment. Each SHA was resolved with `gh api repos/<owner>/<repo>/commits/<tag>`.
3. **A native runner under an unprivileged system user**, kept in `scripts/ci-runner/` (since 2026-11-13 in `github-runner/` of the `self-software-distribution-platform` repository, after a short stay in the `Server` repository's `infras/ci-runner/`, because the runners serve the whole server).
   - **Install script.** Run by the owner, never as root; it asks for sudo only for the system steps.
     - Before any system step it refuses a repository whose visibility (`gh api repos/<repo> --jq .visibility`) is not `private`. The repository override is `RUNNER_REPO`, so a generic exported `REPO` cannot redirect either script. The check runs only at install time.
     - It refuses to run while an installed `tailscaled` is stopped, so that the unit's `/run/tailscale` mask has a directory to cover.
     - The user `gh-runner`, the home `/var/lib/gh-runner` and the label `aevra-home` are constants. `CI_RUNS_ON` is derived from the label.
     - It creates the user with a `nologin` shell and no privileged group, or checks that an existing account is that non-root system account and owns that home.
     - It masks `user@<uid>.service`, disables lingering and removes any crontab of the user.
     - It denies SSH logins as `gh-runner` with the drop-in `/etc/ssh/sshd_config.d/90-aevra-gh-runner.conf` (`DenyUsers gh-runner`). It first runs `sshd -t` on the current configuration and stops without touching the drop-in if that already fails. It leaves a drop-in that already holds exactly that line as it is; otherwise it writes the file and validates it with `sshd -t`. If sshd rejects it, the script puts back the previous state and stops: a drop-in this run created is removed, and an earlier one is restored, so an existing denial is never dropped. It then checks with `sshd -T` that sshd reads it (stopping when `sshd_config` does not include `sshd_config.d`; the output is captured before it is matched, because `grep -q` in a pipe could kill `sshd` with SIGPIPE under `pipefail`), and reloads `ssh.service` when it is active. On this host `sshd_config` includes `sshd_config.d/*.conf` and both `ssh.service` and `ssh.socket` are active; the `sshd-unix-local` instance runs `sshd -i` with the same configuration. `DenyUsers` refuses the login before any session, PAM session or forwarding starts; `Match User gh-runner` with `DisableForwarding yes` would close only forwarding, and a firewall rule on port 22 would miss `/run/ssh-unix-local/socket`. The step runs on every install run and is skipped only when `sshd` or `/etc/ssh/sshd_config.d` is absent. `uninstall.sh` removes the drop-in only with `--purge`, which also deletes the account.
     - On a first install it downloads the pinned runner, verifies its SHA-256, unpacks it as `gh-runner` and registers it as `aevra-home-1`. The short-lived registration token is passed through stdin and never printed. An existing registration is kept as it is.
     - Root creates only the home itself, whose parent `/var/lib` jobs cannot change. `runner/` and `tmp/` below it are job-writable, so they are created, and the tarball is unpacked, as `gh-runner`. A symlink a job plants there then reaches only what `gh-runner` can already change, and any other target makes the command fail (a permission error for a root-owned directory, `EEXIST` or `ENOTDIR` for a file or a dangling link), which stops the script under `set -e`.
     - It installs the unit. When the rendered unit differs from the installed one, it restarts the service, and refuses while the runner is busy.
     - It checks that the runner is online and runs with `no_new_privs`. With `--use`, it checks that the registered runner has the label before it sets `CI_RUNS_ON`.
   - **Service.** `ExecStart=/bin/bash <home>/runner/bin/runsvc.sh` with `WorkingDirectory=<home>/runner`. This is the wrapper that the runner itself keeps current: after a self-update `bin` points to the new version. `KillMode=mixed`: SIGTERM stops the runner gracefully, and then every process left in the cgroup is killed. `After=tailscaled.service` and `PartOf=tailscaled.service` tie the runner to tailscaled for the `/run/tailscale` mask below.
   - **Service hardening:**
     - `ProtectHome=yes` (no access to `/home`);
     - `ProtectSystem=strict` with `ReadWritePaths=` the runner home, and `PrivateTmp`. `strict` leaves the kernel API trees `/dev`, `/proc` and `/sys` writable, including the host's world-writable `/dev/shm` and `/dev/mqueue`, so:
       - `TemporaryFileSystem=/dev/shm:mode=1777,nosuid,nodev,size=2G` gives the service a private, size-capped `/dev/shm` (not hidden: multiprocessing locks need it);
       - `PrivateIPC=yes` gives it its own SysV IPC namespace and `/dev/mqueue` (it does not cover POSIX shared memory, hence the `/dev/shm` mount);
       - `RemoveIPC=yes` removes every SysV and POSIX IPC object `gh-runner` still owns on the host when the unit stops, including the D87 pause;
     - `NoNewPrivileges=yes`;
     - `ProtectKernelModules`, `ProtectControlGroups`, `ProtectClock`, `LockPersonality`, `UMask=0027`;
     - `DevicePolicy=closed` (no GPU, no `/dev/kmsg`; `char-rtc r` is implied by `ProtectClock`, and the `root:clock` 0660 RTC nodes stay closed to `gh-runner`);
     - `InaccessiblePaths=-/run/dbus/system_bus_socket`, which hides the system bus from processes inside the unit, so they cannot ask logind for lingering or make other bus calls directly. sshd denies SSH logins as `gh-runner` (install script above), so job code cannot reach the bus through an SSH session as `gh-runner` either (password logins as other accounts are a residual risk, see Consequences). A `dbus.socket` restart re-creates the socket file and detaches the mask until the runner restarts;
     - `InaccessiblePaths=-/run/tailscale`, which hides tailscaled's world-writable LocalAPI socket. Every tailscaled restart deletes and re-creates `/run/tailscale` (`RuntimeDirectory=tailscale`), and the kernel then drops the mask in the runner's namespace, so `PartOf=` restarts the runner with tailscaled and `After=` makes it stop first and start after tailscaled, also at boot. A tailscaled restart, package upgrades included, therefore waits for the runner to stop (up to `TimeoutStopSec=5min`) and ends the CI job in progress; after a tailscaled crash the tailnet stays down that long. After `systemctl stop tailscaled` the runner stays stopped, which fails closed. If the runner starts while `/run/tailscale` is absent, the `-` prefix skips the mask without a message. Not yet validated on the installed unit (see Validation and the tailnet residual risk);
     - `InaccessiblePaths=-/run/ssh-unix-local`, which hides systemd-ssh-generator's local sshd socket (`/run/ssh-unix-local/socket`, mode 0666). Each connection there is a fresh `sshd -i`, so sshd's `PerSourcePenalties` do not apply, and job code could guess other accounts' passwords there, throttled only by the socket's `PollLimitBurst=50` per 30 s, pam_unix's failure delay and `MaxAuthTries`. Like the D-Bus mask, it holds while the directory persists: re-creating `/run/ssh-unix-local` detaches it until the runner restarts. sshd on loopback TCP port 22 stays reachable (see the sshd residual risk). Not yet validated on the installed unit;
     - `IPAddressDeny=` for the private, CGNAT/tailnet, link-local, multicast and limited-broadcast (`255.255.255.255/32`) ranges of IPv4 and IPv6. It filters only the unit's own sockets: a host daemon that connects on a job's behalf (tailscaled; sshd, which forwards nothing for `gh-runner` logins because the SSH denial refuses them) is outside it;
     - `TMPDIR` on disk, `CPUQuota=800%`, `MemoryMax=16G`, `MemorySwapMax=2G` (a runaway job is OOM-killed instead of filling the host's 8 GB swap; not 0, so host-wide reclaim does not fall on CORE and the services), `TasksMax=4096`, `Nice=10` and low I/O priority.
   - **NoNewPrivileges is set.** It stops setuid/setgid binaries (`crontab`, `su`, `pkexec`, `fusermount3`, `newuidmap`) and file capabilities from raising privileges for job code. `bwrap` keeps working: AppArmor allows the exec from an unconfined task into the `bwrap` profile under `no_new_privs`, and `bwrap` sets `no_new_privs` on its child anyway. systemd 259 does not imply it for a `User=` unit without `SystemCallFilter=`, so the unit sets it explicitly.
   - **Deliberately not set,** because each one breaks the project sandboxes:
     - Any directive that mounts over a path under `/proc`: `ProtectKernelTunables`, `ProtectKernelLogs`, `ProtectHostname`, `ProtectProc`, `ProcSubset`, and `BindPaths`, `ReadOnlyPaths`, `InaccessiblePaths` or `TemporaryFileSystem` entries under `/proc`. `bwrap`'s user namespace locks such a mount, and the kernel then refuses the fresh procfs of `--proc /proc`. Kernel logs and sysctls stay closed to the unprivileged user through `kernel.dmesg_restrict=1`, `/proc/kmsg` mode 0400 and the lack of capabilities. Other processes' command lines do not stay closed; see the residual risks.
     - `RestrictSUIDSGID`: its seccomp filter makes `openat2()` fail with `ENOSYS`.
     - `PrivateNetwork` and `IPAddressDeny=localhost`: they break DNS through the 127.0.0.53 stub and the tests' 127.0.0.1 listeners.
4. **What jobs can reach on the self-hosted runner.** The hosted exclusions (`.github/ci/`) apply unchanged. They select tests; they do not isolate anything.
   - Blocked by the unit: `/home` (owner files, Vault bootstrap, models, `.env`, `data/`), the GPU, direct connections to the LAN, Docker and k3s networks, and limited broadcast.
   - Blocked by sshd (the install script's `DenyUsers` drop-in): SSH logins as `gh-runner`, so a key a job plants in `~/.ssh` opens no session and no TCP or Unix-socket forwarding to the networks, the system D-Bus or host sockets.
   - Still reachable: services listening on loopback or on all addresses, including Vault, Qdrant, PostgreSQL, Redis, MongoDB (27017, the host `mongod`; 27018, Docker), sshd, k3s and CORE when it runs. Their protection is their own authentication, which two of them lack (below).
   - Still reachable around `IPAddressDeny=`: tailnet peers through tailscaled's LocalAPI socket, until the unit's mask on it is validated (see Consequences).
   - Still readable: the command line of every host process, so no secret may be passed as an argument on the host while the runner is installed.
   - Redis on 127.0.0.1:6379 accepts every command without authentication. The host `mongod` on 127.0.0.1:27017 did too until the owner enabled authorization on 2026-11-13. The Docker MongoDB on 27018 runs with `--auth`. sshd on 127.0.0.1:22 accepts password guesses for other accounts, the owner included. These residual risks are the owner's to decide (see Consequences).
5. **Measurements.** Native benchmarks and D87 pause the runner (`systemctl stop aevra-gh-runner`; since ADR-196 all pool instances: `sudo systemctl stop 'aevra-gh-runner@*'`) and keep using the idle-host check. With `KillMode=mixed`, the pause also ends any process a job left behind in the unit, and `RemoveIPC=yes` removes the IPC objects it left. An SSH key a job planted gives no SSH session that could outlive the pause, because sshd denies logins as `gh-runner`.

## Alternatives

- **Pay or fix GitHub billing.** This is the owner's decision. It stays possible: delete `CI_RUNS_ON` and CI is fully GitHub-hosted again.
- **Runner in a Docker container.** `bwrap` inside the container would need seccomp, AppArmor and `/proc` restrictions lifted. That gives weaker kernel isolation for no filesystem benefit over a hardened system service, and the test layout would differ from the Home Server's.
- **Run as the owner's user.** CI jobs would read the owner's home, including the Vault bootstrap file, `.env`, models and `data/`. Rejected.
- **Ephemeral runners with a token service.** Each job would start on a fresh runner. That needs a stored GitHub credential with administration rights, or a GitHub App, which is more attack surface than this private, single-owner repository needs. It can be revisited if collaborators are added, or for the token-bearing `release` job.
- **A per-uid nftables loopback filter or a polkit rule for the runner user.** Not part of this change. `IPAddressDeny=` cannot filter by port, so loopback stays open. A host firewall or polkit change is a separate decision for the owner.
- **A separate machine or VM.** This is better isolation, but no spare host exists. The kit works unchanged on another Ubuntu 24.04 host with the same tools.

## Consequences

- CI runs again with no billing dependency, and pull requests show real checks. Merges can again rest on CI rather than only on local evidence.
- CI jobs share CPU, memory and disk with the Home Server's services. The unit limits CPU and memory; disk is not limited: `/var/lib/gh-runner` is on the root filesystem together with Docker, k3s, the databases and Vault (see the disk residual risk). Runner jobs can disturb native measurements unless the runner is paused.
- One runner runs one job at a time, so the jobs of a run queue up. A full run takes about the length of the test job (about 10 minutes locally) plus the short jobs.
- Code from any branch pushed by someone with write access runs on the Home Server as `gh-runner`. The repository must stay private, and this runner must never be attached to a public repository. `install.sh` refuses a repository that is not private, but only at install time; making the repository public later still requires running `uninstall.sh` first.
- Third-party action code now runs on the persistent host, which is why every remote action is pinned to a commit SHA. Turning on the repository setting that requires SHA pinning is a separate owner decision. It should come only after the pinned files have reached every branch.
- The runner updates itself. A fresh install uses the pinned version and checksum in `install.sh`.
- **Residual risks,** accepted for a private, single-owner repository:
  - **Loopback services.** Jobs can connect to loopback service ports and rely on those services' authentication. Jobs find no credentials for them in files, because `/home` is hidden, but they can read credentials passed on a command line (next point). Two services have no authentication:
    - Redis on 127.0.0.1:6379: a job can read and change its data.
    - MongoDB on 127.0.0.1:27017, the host `mongod`, which is enabled at boot and holds application databases. Until 2026-11-13 `/etc/mongod.conf` had no `security.authorization`, so the server accepted every command without authentication, so a job can read, change or drop its databases and run admin commands. This is separate from the Docker MongoDB on 27018, which runs with `--auth`. The remedy is the owner's, decided before `install.sh --use` and recorded here: (a) accept it as a residual risk, like Redis; (b) set `security.authorization: enabled` in `/etc/mongod.conf` after creating an admin user; or (c) stop and disable that `mongod` if nothing uses it. Changing `/etc/mongod.conf` or restarting `mongod` is a host change outside this change, which `install.sh` does not make. **Owner's choice (2026-11-13): (b), enable authorization.** **Done on 2026-11-13.** The owner created the admin user (`root@admin`) at the password prompt, added `security.authorization: enabled` to `/etc/mongod.conf`, and restarted `mongod` at 11:50:42 (+07). Checked afterwards without credentials: an unauthenticated `listDatabases` returns `Unauthorized`, and `ping` still returns `ok: 1`. Clients of `agent_angi_recipes`, `default_database`, `nutrition_ai` and `steam_db` now need their own users and credentials, passed in a file or the environment, not as arguments.
  - **sshd password logins as other accounts.** `NoNewPrivileges` blocks `su`, `sudo` and `pkexec` inside the unit, but job code can still reach sshd on 127.0.0.1:22 and [::1]:22 and guess the password of another account, including the owner, who is in `sudo` and `docker`. `PasswordAuthentication` is on (the default; `KbdInteractiveAuthentication` is already `no`), and the host has no lockout (no fail2ban, sshguard or `pam_faillock`). Only sshd's `PerSourcePenalties`, pam_unix's failure delay of about 2 s and `MaxAuthTries 6` slow the guessing, and the penalties are keyed per source address, so binding other 127/8 source addresses avoids them. A correct guess gives an owner session outside the unit's cgroup, `IPAddressDeny` and every mount mask. On the local socket `/run/ssh-unix-local/socket` (mode 0666) each connection is a fresh `sshd -i`, so the penalties do not apply at all; the unit hides `/run/ssh-unix-local` for that reason (Service hardening above). Options are listed under the owner's hardening choices below.
  - **Process list and command lines.** `ProtectProc` and `ProcSubset` are unset, because they mount under `/proc`, so jobs can read the argv of every host process in `/proc/<pid>/cmdline`: owner shells, Claude sessions, cron, services, and Docker/k3s healthchecks and `exec` commands. Any secret passed as an argument is readable by CI jobs while it runs; other users' `/proc/<pid>/environ` stays mode 0400. Instances found: the MongoDB healthcheck in `infras/mongo-server/mongo-compose.yaml` passed the root password to `mongosh --password` every 10 seconds (confirmed on this host: the value was visible in host `/proc`); it was fixed and applied on 2026-11-13 (see below). Still current: `infras/scripts/manage_server_secrets.py` does the same during a MongoDB rotation, and the commands that `mongo-server/scripts/create-database-template.py` prints pass passwords as arguments. Rule while the runner is installed: pass secrets through stdin, environment variables or files, never as arguments.
  - **SSH as `gh-runner`: denied by sshd.** A job can still write `~gh-runner/.ssh/authorized_keys`, but the install script's `DenyUsers gh-runner` drop-in makes sshd refuse every login as `gh-runner`, on port 22 and on `/run/ssh-unix-local/socket` (`sshd-unix-local.socket`, mode 0666, which the unit also hides from processes inside it, as long as the mask holds). Without the denial, a planted key would be a standing login that works with no job running, survives `systemctl stop` including the D87 pause, and makes sshd forward TCP and Unix sockets from outside `IPAddressDeny` and the mount sandbox (loopback-only services such as Redis, the LAN, the tailnet, the Docker and k3s networks, the system D-Bus, tailscaled's LocalAPI socket). What remains is that the denial is host configuration outside the unit: it holds while the drop-in stays in `/etc/ssh/sshd_config.d` and sshd reads it, which `install.sh` checks with `sshd -T` on every run. `uninstall.sh` still deletes `~/.ssh` once the user's processes are gone, with or without `--purge`, as defense in depth.
  - **Tailnet through tailscaled.** tailscaled's LocalAPI socket `/run/tailscale/tailscaled.sock` is mode 0666. Through it (`POST /localapi/v0/dial`, or `tailscale nc`), job code can make root `tailscaled` open connections to other tailnet peers, outside `IPAddressDeny`, and read the full peer list (`/localapi/v0/status`). The unit's `InaccessiblePaths=-/run/tailscale` with `PartOf=`/`After=tailscaled.service` is meant to close this, but it is not yet validated on the installed unit. Until it is, tailnet peers count as reachable from CI jobs. An SSH session as `gh-runner` cannot forward to the socket, because sshd denies those logins.
  - **Abstract Unix sockets** are not covered by the mount sandbox.
  - **Disk.** No disk limit: `/var/lib/gh-runner` is on the root ext4 filesystem (`/dev/sda4`, mounted without quotas) together with Docker, k3s, PostgreSQL, MongoDB, Redis and Vault. A job, through a runaway test or a compromised dependency, or plain growth in `~/.cache/uv`, `runner/_work`, `runner/_diag` and `tmp/`, can fill it down to the 5% that ext4 keeps for root (about 46 GB here). The data services that do not run as root (PostgreSQL, MongoDB, Redis, Vault) then fail with `ENOSPC` at the same point as `gh-runner`; root daemons such as dockerd, containerd and k3s keep the reserve, and k3s's kubelet starts evicting pods earlier, once free space drops below its threshold. Files left under `/var/lib/gh-runner` stay after the job until someone removes them. The unit is unchanged for this; the options are listed under the owner's hardening choices below.
  - **No isolation between jobs.** The runner is persistent, and every job runs as the same user with a writable runner directory. Job code can:
    - leave modified files that affect later jobs: `runner/bin`, `.env`, `.path`, `~/.gitconfig`, `~/.cache/uv`;
    - read later steps' environment, including the `release` job's `contents: write` token;
    - read the runner credentials and impersonate the runner.

    Processes that a job starts with an empty environment escape the runner's own cleanup between jobs. `KillMode=mixed` ends them when the service stops.
  - **Required before `install.sh --use`** (an owner change in `infras/`; it recreates the mongo container, so this change does not apply it): take the root password off the MongoDB healthcheck's command line. The healthcheck can drop `--username` and `--password` entirely, because `db.adminCommand({ping: 1})` needs no authentication, or read the credential from a file or stdin. Done in the compose file on 2026-11-12: commit `71aa2c0` in the `Server` repository (the parent of `infras/`, which has no remote) drops the three credential arguments; an unauthenticated `ping` in the running container returned exit 0, and the infras template tests pass (6 passed). Applied on 2026-11-13 with the owner's approval: `docker compose --env-file mongo-server/mongo.env -f mongo-server/mongo-compose.yaml up -d --no-deps mongo` from `infras/` (a dry run first showed only `mongo` recreated) recreated the container, which was healthy after about 9 s with the same two named volumes. Its healthcheck has no credentials; a 30-second scan of `/proc/*/cmdline` (three healthcheck cycles) found no `mongosh` with `--password`; an unauthenticated `listDatabases` is still refused (`Unauthorized`). `mongo-storage-monitor` was not touched. The commands that `mongo-server/scripts/create-database-template.py` prints also pass passwords as arguments; do not run them while the runner is installed. Do not run a MongoDB rotation with `manage_server_secrets.py` while the runner is installed until it does the same. Also required: authorization on the host `mongod` on 127.0.0.1:27017, which the owner chose on 2026-11-13 and has not made yet (steps under Loopback services above).
  - **Hardening the owner can choose:**
    - authentication on Redis (the host `mongod` on 127.0.0.1:27017 has had authorization since 2026-11-13, and the Docker MongoDB on 27018 runs with `--auth`);
    - sshd password logins, recommended before `--use` (no change to sshd or its socket units is part of this change):
      - `PasswordAuthentication no` host-wide, which covers loopback TCP and the Unix socket, once the owner has checked that key login works from every client they use;
      - if password logins stay for remote clients, both together: a `Match Address 127.0.0.0/8,::1` block with `PasswordAuthentication no` for loopback TCP, and masking or disabling `sshd-unix-local.socket` (or booting with `systemd.ssh_auto=no`). The `Match` block alone does not close the Unix socket, because sshd sees that peer as `UNKNOWN` and `Match Address` never matches it; until then the unit's `/run/ssh-unix-local` mask is the only cover there;
    - a disk limit for `/var/lib/gh-runner`:
      - a separate partition, or a preallocated, loop-mounted ext4 image of fixed size (for example 100G), mounted at `/var/lib/gh-runner`, with `RequiresMountsFor=/var/lib/gh-runner` added to the unit so the runner never starts on the root filesystem when the mount is missing;
      - `StateDirectory=gh-runner` with `StateDirectoryQuota=` (systemd 258 and later; this host has 259). It needs project quotas on the root ext4 (`tune2fs -O quota -Q prjquota`, which runs only with the filesystem unmounted) and changes how `install.sh` handles directory ownership;
      - a free-space check in the self-hosted preflight, which only catches accidents, because job code can change the preflight;
      - periodic cleanup of `~/.cache/uv`, `runner/_work` and `tmp/`;
    - for the tailscaled socket, instead of restarting the runner with tailscaled: a tailscaled drop-in with `RuntimeDirectoryPreserve=yes`, which keeps `/run/tailscale` across tailscaled restarts so the unit's mask holds (tailscaled re-creates only the socket file), or restricting access to the LocalAPI socket on the host;
    - a per-uid loopback firewall;
    - running `release` on a one-shot just-in-time runner or from the owner's shell;
    - remounting the host `/proc` with `hidepid=invisible` and a `gid=` exemption group, for example for `polkitd`, which runs as a non-root user. A host-wide `hidepid` can affect logind and polkit, and it was not tested here;
    - `PrivatePIDs=yes` (systemd 257 and later; this host has 259), which gives the service a fresh `/proc` showing only its own processes without mounting over subpaths. Untested: it needs a check that `bwrap --proc /proc` still works under it and that `runsvc.sh` handles SIGTERM as PID 1.
- **Recovery after a suspected compromise.** Run `uninstall.sh --purge`, check the runner list on GitHub and remove any runner you do not expect, then run `install.sh` again. The uninstall deregisters the runner through the GitHub API from the owner's `gh` login and deletes the runner tree; it never executes code from that tree outside the unit, because job code can rewrite it. A plain rerun of `install.sh` keeps the existing runner tree as it is and does not repair tampered files.

## Rollback

`uninstall.sh` (now `github-runner/uninstall.sh` in the `self-software-distribution-platform` repository) first deletes `CI_RUNS_ON`; if it cannot read or delete the variable, it stops with an error and leaves the runner running. Before anything changes, it checks that the account is the non-root system account whose home is `/var/lib/gh-runner`. It then stops the service, kills every leftover `gh-runner` process, disables lingering and removes any crontab. Once no `gh-runner` process is left, it deletes `~gh-runner/.ssh`, with or without `--purge`, as defense in depth, since sshd already denies logins as `gh-runner`; a plain uninstall keeps the account, the rest of its home and the sshd denial. It deregisters the runner through the GitHub API (`DELETE repos/<repo>/actions/runners/<id>`, with the id looked up by name on GitHub, not read from the job-writable `.runner` file), so no removal token reaches `gh-runner` and nothing from the runner tree runs outside the unit. It then deletes the runner tree as root and removes the service. `--purge` also removes the sshd drop-in (reloading `ssh.service` when it is active) and deletes the user and its home. The workflow keeps working on GitHub-hosted runners with no further change.
