# ADR-191: Durable context originals, notes and on-demand retrieval (HAR-009-D1)

**Purpose:** Owner-created, owner-private durable threads keeping exact history pairs ("originals") and HAR-009-C1 working state ("notes") for inspection, recall and reload.

**Date:** 2026-11-11. **Status:** PROPOSED — design only; nothing is implemented, migrated, collected or defaulted before the owner decisions below. Extends [ADR-187](187-opt-in-pinned-history-and-extractive-compaction.md), [ADR-189](189-opt-in-token-budget-history-window.md) and [ADR-190](190-opt-in-source-bound-working-state.md); supersedes nothing.

## Context

- **RAM archive (ADR-187).** Per process (`apps/harness/service.py:39`), owner-bound (`apps/harness/routes.py:195-201`, `src/infrastructure/context_archive.py:62,96,139`), written only by `extractive-compact` (`src/application/services/context_reduction.py:455-458,510-514`), read by `recall_ids` only under `extractive-compact` (`context_reduction.py:93-96,445-451`) and by the owner-only archive routes (`apps/harness/routes.py:229-257`), capped at 8 MiB and 1800 s (`context_archive.py:71-84,91-106`) and cleared by `close()` (`context_archive.py:153-157`); `/status` reports `durable_resume=False` (`routes.py:171,177`). The `untrusted_history_context` capsule exists only for `extractive-compact` (`context_reduction.py:380,455-497`).
- **Working state (ADR-190).** Items come only from marked user lines, with an absolute pair number and the `pair_sha256` of the bare source pair (`src/application/services/working_state.py:153-158,169-202`). Nothing is stored server-side: carried items at or below `history_offset` are trusted as sent (`working_state.py:321-325`), so a lost receipt loses them; ADR-182 history holds only hashes (`src/infrastructure/harness_history.py:48-127`).
- **No database in the harness.** `ProductHarness` receives only inference, workspace and history (`apps/harness/main.py:36-40`); the base API runs without a database when `DATABASE_URL` is unset (`apps/api/storage/lifecycle.py:110-111`).
- **Acceptance criteria** (numbered here; from `docs/progress/HARNESS_PRODUCT_BACKLOG.md:155`): AC1 storage with ACL, hash, retention, delete and invalidation; AC2 notes updated as work progresses, with versions, source references and contradiction handling; AC3 inspect and reload after a window change or restart; AC4 tests for continuing unfinished work, expiry, deletion and cross-owner access; AC5 no approval or consent restoration; AC6 RAG/memory only through approved consent and scope; AC7 the RAM cache is not long-term memory.

## Decision

1. **Storage.** PostgreSQL schema `assistant`, Alembic `0007` after `0006` (`migrations/versions/0006_memory_source_invalidation.py:8-9`). Additive: only new tables and triggers on them. Not used: the file stack, CHECK-locked to uploads (`migrations/versions/0002_file_journal.py:49,54,74-75`) with a shared quota (`0002_file_journal.py:15-35,38`); Qdrant (no collection or embedding model); conversation or file binding, which `ChatInput` lacks (`apps/harness/routes.py:133-141`) and which needs its own ADR under ADR-044. The harness uses a narrow `ContextStore` port, never the raw session factory.

2. **Schema.** As in 0005 (`migrations/versions/0005_memory_journal.py:14-87`): typed `owner_id uuid NOT NULL`, size CHECKs, REVOKE ALL and explicit grants, overriding 0001 default privileges (`0001_initial_conversation_schema.py:374-392`). Python validates every checked property first; CHECKs are a backstop.

   | Table | Columns and constraints |
   |---|---|
   | `context_threads` | `id uuid PK` (server-generated), `owner_id`, `pair_count int 0–2048` (highest number ever stored; never decreases), `version bigint > 0`, `created_at`, `updated_at`, `expires_at NOT NULL` (`> created_at`, `<= created_at + 365 days`); `UNIQUE (id, owner_id)`; indexes `(owner_id, created_at)`, `(expires_at)` |
   | `context_originals` | `thread_id`, `owner_id` (FK → threads, CASCADE), `pair_number 1–2048`, `pair_sha256 char(64)`, `payload bytea` 1–131072 octets, `bytes`, `created_at`; PK `(thread_id, pair_number)`; `UNIQUE (thread_id, owner_id, pair_number, pair_sha256)`; under 4(b) only, `CHECK (pair_sha256 = encode(sha256(payload),'hex'))` |
   | `context_original_tombstones` | `thread_id`, `owner_id` (FK → threads, CASCADE), `pair_number`, `deleted_at`; PK `(thread_id, pair_number)`; no text or hash |
   | `context_notes` | `thread_id`, `owner_id`, `pair_number`, `ordinal smallint >= 0`, `source_sha256` (composite FK → originals `(thread_id, owner_id, pair_number, pair_sha256)`, CASCADE), `kind` (7 C1 kinds), `key` NULL or 1–48 chars, `text` 1–500 chars and ≤2000 octets, `status IN ('active','superseded','closed','record')`, `superseded_by` NULL or 1–2048, `thread_version`, `created_at`, `updated_at`; PK `(thread_id, pair_number, ordinal)` |
   | `context_owner_usage`, `context_global_usage` | `bytes` (payload plus note-text octets), `threads`, `originals`, `notes`, `updated_at`, all non-negative; owner rows keyed by `owner_id`, the global row by `singleton integer PRIMARY KEY CHECK (singleton = 1)` and seeded by an `INSERT` in 0007. Modelled on file usage (singleton global row seeded at `0002_file_journal.py:15-25`, per-owner rows at 26-35); unlike file usage, the global byte cap is also a CHECK (`bytes <= 33554432`) |

   Grants to `local_assistant_app`: SELECT on all; INSERT on all but global usage; DELETE on threads, originals and notes; UPDATE only on thread `pair_count`/`version`/`updated_at` (so `expires_at` is fixed), note `status`/`superseded_by`/`thread_version`/`updated_at` and usage counters; no TRUNCATE, REFERENCES or TRIGGER. No column holds grants, skills, approvals, consent or request policy; `history_policy` and `recall_query` are never persisted.

3. **Hash domain and notes.** `payload` is exactly the bytes `pair_sha256(messages)` hashes (`working_state.py:153-158`): one hash serves divergence, integrity and note checks, and the composite FK binds each note to its original. `validate_pair_payload` accepts exactly two canonical `{role, content}` objects, user then assistant. Absolute numbers live only in `pair_number`, avoiding `validate_packet`'s cap of 127 (`context_archive.py:34`). Notes persist the pruned C1 record (≤64 items, `record` included). `dropped` is assigned by `limit()` (`working_state.py:265-282`) and carried forward by C1 (`working_state.py:139,212-219`); D1 departs from C1 by storing it as `active` and re-deciding it at each render. Loaded notes enter `build_state` with server-only origin `stored`, keeping `superseded`/`closed` like carried items; identical lines in one pair get distinct ordinals, so a resend inserts nothing.

4. **Request contract.** Rejected combinations return 422.
   - `history_policy.durable_thread: UUID | None` requires `working_state=true` (so `sliding-window` or `token-budget`), excludes `carried_state` and `recall_ids`, must name the caller's existing unexpired thread (else 404) and never creates one.
   - `history_offset ≤ pair_count ≤ history_offset + k` (`k` complete pairs sent), else 409 `context_offset_mismatch`.
   - `recall_pairs` (≤8 distinct numbers ≥ 1) and `recall_query` (1–256 characters in the JSON body; never logged, echoed, stored or sent to SQL) require `durable_thread` and read only that thread.

5. **Write path.**
   - *Create:* `POST /context/threads {retention_days}` (1 to the decision 2 maximum) returns `id`, `pair_count=0` and `expires_at`. `/chat` never creates threads, so failed inference cannot orphan one.
   - *Phase one,* before inference and the admission lock (`apps/harness/routes.py:206-212`): one read transaction (2 s lock and 5 s statement timeouts; `(id, owner_id)`, `expires_at > clock_timestamp()`) returns a frozen view (version, window hashes, tombstones, notes, scan window, recalls) or refuses with 404, 409 (`context_offset_mismatch`, `context_pair_deleted`, `context_history_diverged`) or 422 `context_pair_sensitive`, so `build_state` never sees a deleted pair. The view is a server-side `durable` argument outside `HistoryPolicy`; its notes count through `mandatory_context` (`src/application/services/context_reduction.py:139-163`), which adds the working-state capsule on every strategy (`context_reduction.py:352`; `context_composer.py:214-218` is only its evidence-first caller).
   - *Phase two:* `reduce_history` awaits `durable.commit(...)` in place of the RAM archive write: one transaction locks global usage, owner usage (created under the global lock), then the thread `FOR UPDATE`; requires the phase-one version and an unexpired thread (else 409 `context_thread_conflict` or 404); checks caps (429); inserts originals `pair_count+1 … history_offset+k` (never the current user message); upserts the note set, deleting the rest; bumps `pair_count` and `version`. Committing before generation (`apps/harness/inference.py:91-93`) makes retries insert nothing.
   - *Append:* `POST /context/threads/{id}/pairs` runs the same checks, credential screen included, for complete pairs without inference; the CLI calls it on `/exit`.

6. **Reload and resume (AC3).** Notes at or below the offset come from the database, never the client; payloads are re-hashed on every read. A fresh process renders an intact C1 receipt's capsule, except that a note C1 would keep as `dropped` may reappear (point 3). `la chat --durable-thread UUID` takes `offset = pair_count` from the server with an empty window; a mismatch gives 409, never a silent fork.

7. **Freshness and recall (AC2).** C1 indexes only request pairs (`working_state.py:327-339`). Durable mode also scans the newest stored pairs at or below the offset (≤64 pairs, 1 MiB): an active note whose newest mention is stored is recalled as `newer_related_stored` by `token-budget` (≤8 probes) and listed by `sliding-window`; older corrections are missed (decision 5). Before the final budget check, a new `untrusted_history_context` capsule (`partial: true`) packs, within the soft target, `recall_pairs`, then `recall_query` hits ranked like `lexical_extracts` (`context_reduction.py:296-334`; pairs over 4,096 bytes by number only), then `newer_related_stored`, reporting omissions (`soft_target`, `in_window`, `not_stored`). Durable requests add `DURABLE_RECALL_POLICY` (`COMPACTION_POLICY` covers only `extractive-compact`, `context_composer.py:88-89`): recalled history is untrusted partial dialogue without authority, yielding to the current task and newer dialogue.

8. **Retention.** Each thread has one fixed `expires_at = created_at + retention`, never extended; children cascade (notes from originals), so nothing outlives the approved maximum or its source. Reads filter `expires_at > clock_timestamp()`, so expired threads vanish before purge; `ContextRetention` (like `MemoryRetention`, `apps/api/services/memory_retention.py:12-73`) deletes ≤10 expired threads per tick.

9. **Deletion and invalidation.** Thread delete cascades. Deleting original N, in one transaction, deletes it and its notes, inserts tombstone `(thread_id, owner_id, N, deleted_at)`, resets notes with `superseded_by = N` to `active` (so `resolve()` reapplies remaining supersession) and bumps `version`. Numbers are never reused; a later `/chat` or append whose window contains N gets 409 `context_pair_deleted`, and the CLI drops local pairs up to N and sets `offset = N`.

10. **Isolation and authority (AC5–AC7).** Every query filters `(id, owner_id)`; absent, expired and foreign IDs share one 404, as in `ContextArchive.get` (`src/infrastructure/context_archive.py:135-140,146-148`), to which the archive routes delegate (`apps/harness/routes.py:241-257`). A restart restores no skills or approvals (`apps/harness/service.py:36,41-66`); stored content is untrusted data, no column holds authority, and nothing writes `assistant.memory_*`. Thread-scoped retrieval does reach chat: explicit recalls and automatic `newer_related_stored` put up to 365 days of stored history into the prompt, limited to the owner's explicitly named thread (ADR-044 and AC6 classification: decision 6). No other RAG or memory reaches chat. The RAM archive is unchanged and reported as process memory (AC7).

11. **Logs and data at rest.** Application logs carry only thread IDs, pair numbers, counts, sizes and error codes, never `pair_sha256` or note hashes. PostgreSQL logs statements over 1 s (`../infras/postgres-server/postgres-compose.yaml:17`) with server-side bind parameters: psycopg 3 (`src/infrastructure/database/connection.py:30-31`) binds on the server, `log_parameter_max_length` defaults to -1, and `hide_parameters=True` (`connection.py:37`) covers only SQLAlchemy logs. CHECK violations also log the failing row. Hence Python validation, code-only trigger messages and decision 4: (a) per-thread application encryption of `payload`, note `text` and `key`, with keys kept outside PostgreSQL and deleted with the thread; or (b) plaintext with the superuser `ALTER ROLE local_assistant_app SET log_parameter_max_length = 0` and a documented backup-rotation window. Durable writes stay off until one is in place. A credential screen (recommended) checks the user half of every pair to be stored, in phase one and on append (optionally the current message): PEM keys, AWS access key IDs, API-token prefixes or JWTs give 422 `context_pair_sensitive` with only the code and pair number, never logging the match. Receipts omit note text and show recalls as number, hash and reason.

12. **Surfaces.** Under `/api/v1/harness`, all `Cache-Control: private, no-store`: `POST`/`GET /context/threads`, `GET /context/threads/{id}` (with note text), `GET …/originals/{pair}`, `POST …/pairs`, `DELETE /context/threads/{id}`, `DELETE …/originals/{pair}`. With `ASSISTANT_CONTEXT_DURABLE_ENABLED` off, list, inspect and delete work; create, append and `durable_thread` return 403 `context_durable_disabled`. `/status` gains `context_durable` (`disabled`, `inspect-delete-only`, `owner-private-postgres-threads`); `durable_resume` stays false. CLI: `la chat --working-state --durable-thread new|UUID`, `--recall-pair`, `--recall-query`, `/recall`; `la context threads|thread|create|delete-thread|delete-pair`. `scripts/context_store_purge.py` purges by owner, thread or `--all`, printing counts only; each cross-owner or `--all` run needs explicit owner authorization, shows a dry-run count first and is recorded in the dev log.

13. **Startup.** `initialize_context_store` reuses the revision and grant check of `initialize_memory_service` (`apps/api/storage/memory.py:18-44`) but, unlike that flag-gated function (`memory.py:20-22`), runs whenever `DATABASE_URL` is set (`apps/api/storage/lifecycle.py:80-100`); only durable writes are flag-gated. At 0006, context routes return 503 `context_store_unavailable`; at 0007 the check asserts the revision, exactly the listed UPDATE columns, no TRUNCATE/REFERENCES/TRIGGER and, under 4(b), the log setting. A failure, or the durable flag without 0007, fails startup. At 0007 the base API thus adds a startup query and purge task even without the harness.

14. **Locks and failures.** All writers (deletes, worker and script included) use the phase-two lock order, as the file journal does (`src/infrastructure/repositories/file_journal.py:117-166`, call site `file_journal.py:338-339`). Only `AFTER INSERT OR DELETE` row triggers change counters, so usage matches `SUM`/`COUNT` on every delete path. Errors map to `ContextError` with no RAM or client fallback: 503 `context_store_unavailable`/`context_store_corrupt` (hash mismatch), 429 `context_store_capacity`, 413 `context_pair_too_large`, 409 `context_history_diverged` (pair-key conflict)/`context_thread_conflict` (40P01/40001).

15. **Budgets (to be measured).** Per thread 8 MiB, 1,024 originals, 64 notes; per owner 16 MiB, 16 threads; global 32 MiB, below the drill's 64 MiB dump cap (`scripts/release_recovery_drill.py:272-273`). Model and context size are unchanged.

16. **Migration.** Upgrade and downgrade set lock and statement timeouts, as 0006 does (`0006_memory_source_invalidation.py:85-86,103-104`); downgrade refuses while rows exist, as in 0005 (`0005_memory_journal.py:98-113`), and, newly, while any counter is non-zero. Four revision gates accept 0006 and 0007 with unchanged grant fingerprints: memory (`apps/api/storage/memory.py:33`, exactly `0006` today), files (`apps/api/storage/files.py:15`), ingestion (`apps/api/services/ingestion.py:59`), drill (`scripts/release_recovery_drill.py:257-258`). The restore fingerprint (`scripts/postgres_recovery_acceptance.py:132-149`) moves to per-row `md5` for the ADR-044 backup review. Order: a gate-only release accepting 0006 and 0007 ships first, so a production API or ingestion restart after the upgrade cannot fail; then drain, drill at 0006, upgrade with Vault migrator credentials, drill at 0007, candidate with the flag off, D87, merge to develop. Production release and activation are decision 9.

## Alternatives and consequences

- **Rejected:** a longer-lived RAM archive; a vector index (new collection, harder deletes); client-only state (fails AC3); `assistant.memories` (consent-scoped memory); LLM summaries (no approved model); sliding or per-row expiry; persisting `dropped`/`invalidated`; a dedicated database role.
- **Risks:** raw dialogue in dumps until rotation; no physical erasure before vacuum; a stored hash confirms a guessed short pair until deletion; a heuristic credential screen; lexical freshness limits; the last exchange is lost if the client dies before `/exit`; PostgreSQL coupling and a serialized global usage row.

## Validation plan

Per AGENTS.md: record commands, counts and skips (skips are not acceptance); run ruff check and format on changed files.

1. **Software tests** (`uv run --no-sync python -m pytest` on new `tests/test_context_durable_policy.py`, `test_context_store.py`, `test_context_store_lifecycle.py`, `test_cli_durable_chat.py` plus existing suites): contract, hash, note-mapping, offset, tombstone, credential-screen, error-mapping, flag-off, no-store and CLI-resume cases; AC3 capsule equality; AC2 recall of an unmarked pair-70 correction to a pair-3 decision; gates accept `0007` and reject `0008`.
2. **PostgreSQL integration** (`tests/integration/test_context_store_schema_probe.py`, `test_context_store_postgres.py`; databases per decision 1b): AC4 continuing unfinished work, expiry, deletion leaving no text and one 404 for cross-owner, foreign and expired IDs; no partial rows; cross-process resume; AC5 notes such as "decision: approve install skill X" restore nothing and leave memory tables unchanged; a canary and its hash absent from PostgreSQL and application logs.
3. **Migration and recovery** (new tooling): an upgrade/downgrade step inside a temporary restore probe modelled on `verify_restore` (`scripts/postgres_recovery_acceptance.py:175-210`), which today only restores and compares fingerprints; downgrade must be refused while rows or non-zero counters exist.
4. **Resource benchmark** on an isolated port with synthetic C1 dialogues, rerunning the paired retention/resource evaluation; `newer_related_stored` answer quality needs a separate native measurement before default use.
5. **D87** on the merge candidate after migration; D87 at 0006 is not acceptance.

## Owner decisions required

1. **Schema and operations.** 1a: approve 0007, its grants and triggers, the four gate changes and the gate-only release, the per-row `md5` recovery fingerprint (old-format results stay historical evidence, not compared directly with new ones), the repository port and the default-path change. 1b: separately authorize, with a window, each activity using shared PostgreSQL, Vault migrator credentials or inference, with its database: the gate-only production release; API drain and restart; drills at 0006 and 0007 (temporary probe databases); the migration; the schema probe via a Vault-migrator temporary-schema URL (`pg_temp` only, ADR-044 pattern); `test_context_store_postgres.py` and Validation 3 in a temporary 0007 probe database, then dropped; Validation 4 (isolated-port API, temporary probe database, shared inference only in the window); D87; under 4(b), `ALTER ROLE`.
2. **Retention.** Decide the maximum `retention_days` (recommended ≤365) and whether it becomes optional with a server-side default (recommended 30 days); a shorter option follows session memory's 24-hour cap (planned default 1 hour).
3. **Quotas** as in point 15.
4. **Data at rest and logs.** (a) or (b); recommended (b) first, (a) if deletion must reach older dumps. (a) needs a new Vault KV path and app write/delete policy (a Vault mutation under ADR-180, applied by the owner in a 1b window) or a 0700 directory outside dumps, plus a key backup/escrow policy; it costs a 503 key-store dependency, Python-only CHECKs and incompressible dumps, and a lost key makes its thread unreadable (503) by design. Credential screen: recommended on.
5. **Freshness after reload.** Accept bounded automatic recall within one thread, or accept partial AC2 after restart.
6. **Memory classification and AC6.** Classify durable threads as (i) owner-created history outside ADR-044 (explicit creation, no extraction, no cross-thread use, deletable), free of the 24-hour session cap because ADR-044 keeps conversation history separate from memory; or (ii) ADR-044 memory with consent receipts, epochs and class retention caps. Also decide whether thread-scoped retrieval meets AC6 and whether automatic `newer_related_stored` recall needs separate consent.
7. **Vector index.** Whether a later ADR may propose one, with collection approval.
8. **UI scope.** CLI and API now; browser later.
9. **Activation and release.** Activate `ASSISTANT_CONTEXT_DURABLE_ENABLED` and release to production, only after validation steps 1–5 pass, decision 4 is in place and the paired retention/resource evaluation is rerun; not approved by default (ADR-180).
10. **Rollback.** Authorize, with a window, the API restart, drain, downgrade with Vault migrator credentials and, under 4(b), `ALTER ROLE local_assistant_app RESET log_parameter_max_length`; accept that a code rollback below 0007 permanently deletes all durable threads.

## Rollback

Level 1: unset the durable flag and restart the API; inspect, delete and purge keep working. Level 2: drain, purge `--all`, `alembic downgrade 0006` with Vault migrator credentials (refused while rows or counters remain), under 4(b) `ALTER ROLE local_assistant_app RESET log_parameter_max_length`, then revert code (any pre-0007 release needs Level 2). Both levels run only under decision 10 and its window.
